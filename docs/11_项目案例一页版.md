# Resolve｜AI 协作决策工具

## 项目概述

Resolve 面向产品经理和项目负责人，将会议和聊天中分散的目标、限制、证据与分歧，转化为可确认、可检查、可追溯的决策过程。AI 负责整理、追问、探索和检查，人类保留需求价值判断与最终决定权。

![Resolve 冲突关系图](assets/03-conflict.png)

## 问题

复杂产品决策很少缺少“一个答案”，更常见的问题是：参与者表达没有被确认、“必须”可能只是偏好或假设、模型在信息不足时仍给出看似完整的建议，以及最终方案无法追溯到证据和责任人。

因此，Resolve 不把产品做成另一个聊天窗口，而是把模型输出转换成需求、约束、冲突、信息缺口、方案、检查结果、异议和决策记录等产品对象。

## MVP 取舍

- 只完整实现“工作 → 产品与研发”，生活、学习和其他工作领域只保留扩展入口。
- 用单操作者切换角色模拟协作，不实现登录、邀请、企业权限和多人实时同步。
- 完成前端、Node.js API、SQLite 和真实模型调用的纵向闭环。
- 模型失败时保留输入并允许重试，不使用预置数据冒充实时结果。
- 预置“AI 自动退款”案例供无密钥体验。

## 核心流程

`描述问题 → AI 整理 → 各方确认 → 需求判断 → 冲突与澄清 → 生成并检查方案 → 审阅与异议 → 负责人确认 → 决策记录`

模型任务采用严格 JSON Schema；程序负责阶段、身份、版本和门槛。未经本人确认的观点、缺少关键证据的方案、未处理异议和受新异议影响的方案，不能进入最终确认。

## 关键产品判断

1. **信息不足也是有效结果**：模型应该停下来提问，而不是补全一个虚假的确定答案。
2. **方案检查必须改变操作权限**：检查未通过的方案不能选择，不能只显示一个风险标签。
3. **AI 不做最终价值判断**：需求是否继续、接受什么代价和最终选择哪个方案，都由负责人确认。
4. **模型选型服务于任务**：使用同一测试集比较质量、延迟和成本，不以“更大模型”替代评测。

## 已完成验证

| 验证 | 结果 | 能说明什么 |
|---|---|---|
| 三模型 Smoke | Plus 连续 3 轮 100%；Max 两轮平均 95%；Flash 两轮 30% | 当前结构化任务选择 Plus 更合适 |
| Plus Holdout | 5/5 | 在少量未参与首轮提示调整的案例上没有立即失效 |
| 纵向流程 | 3 个案例最终均至少完整通过一次 | 创建、停止、补证据、重算和留档可以形成闭环 |
| 早期基线对照 | 一次性建议 78.6%；Resolve 结构化入口 95.3% | 结构化契约在 6 个内部案例中减少了约束误判和人工边界遗漏 |
| 自动化接口测试 | 关键门槛、身份、事件和重启恢复通过 | 状态规则不只存在于页面文案 |

这些结果均来自内部构造案例，不能代替真实用户效果或外部盲测。

## 一次关键迭代

首次真实纵向试跑时，方案检查正确判断“没有方案可以直接通过”，但页面只有禁用状态，没有让用户补充证据后继续的出口；同时发现参与者已确认观点没有完整进入后续模型上下文。

因此增加了“补充信息 → 重新生成方案 → 重新检查”的恢复路径，并修正上下文组装。回归时系统先因证据不足安全停住，补入可追溯证据后完成选择和留档。这个问题促使产品从“会展示风险”变成“能够从风险状态恢复”。

## 当前边界

- 尚未完成真实用户验证，不能据此证明产品价值和使用意愿。
- 当前不是正式多智能体系统，更准确的定义是模块化 AI 工作流、确定性状态机和人工确认节点。
- 尚未实现真实多人协作、完整版本重开、异议后的自动局部再生成和线上生产部署。

## 项目职责

产品定位与范围取舍、Mini PRD、信息架构和交互规则、模型选型、提示与结构化输出设计、评测集与失败分类、AI 辅助实现、流程验收和迭代复盘。
