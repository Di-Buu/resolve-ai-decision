> 文档版本：V1.2

## 1. 产品背景

在工作、生活和学习中，人们经常面对多人参与、目标不同、约束复杂、信息不完整且意见持续变化的决策。

现有方式通常是群聊、会议、表格、投票或直接询问通用聊天机器人。它们能解决部分问题，但很难持续完成：理解每个人真正想要什么；区分需求、偏好、硬约束和未经验证的说法；判断某项要求是否值得继续；找出真正冲突；补齐关键信息；探索不同权衡方案；处理异议和变化；留下可追溯的决策依据。

Resolve 希望把一个混乱的复杂决策过程，转化为结构化、可协商、可解释、可执行、可追溯的过程。

当前判断主要来自桌面调研、竞品分析与场景假设，尚未经过系统的真实用户访谈。因此，需求强度、使用意愿和商业价值仍需通过用户访谈与 MVP 实验进一步验证。

## 2. 产品定位

### 2.1 产品愿景

Resolve 是一个面向工作、生活、学习等场景的 AI 协作决策平台。

当参与者存在不同目标、需求、约束和偏好时，Resolve 利用 AI 理解各方观点、挑战缺乏证据的要求、发现冲突、识别信息缺口、主动澄清、探索可行方案、检查风险、处理异议与变化，最终辅助人类形成决定。

### 2.2 核心原则

> Resolve 追求更高质量的决策，而不是不惜一切代价达成共识。

因此，“需要补充信息”“需要负责人取舍”“当前无可行方案”都是合法结果。AI 没有需求否决权，也没有最终决策权。

### 2.3 产品形态

AI 主要隐藏在后台。界面应展示结构化产品对象，不展示多个 Agent 彼此聊天。只有需要用户补充或确认时，才使用简短自然语言交互。

## 3. 平台场景架构

| 一级场景 | 二级场景示例 | V1 状态 |
|---|---|---|
| 工作 | 产品与研发、项目资源、团队协作、商务合作、招聘人才 | 产品与研发开放，其余“即将开放” |
| 生活 | 旅行、聚餐、共同消费、家庭选择、社交活动 | 展示入口，不开放完整流程 |
| 学习 | 小组作业、选题、分工、竞赛、升学、学习路径 | 展示入口，不开放完整流程 |

平台开发范围与平台假设验证范围分开：产品只完整实现“工作 → 产品与研发”，评测集可加入生活与学习案例，验证底层能力能否跨场景迁移。

## 4. MVP 选择与目标用户

### 4.1 为什么先做产品与研发

- 目标、工期、资源、效果、成本和风险之间的冲突密度高。
- 多角色参与和意见变化常见，适合验证持续决策状态。
- 多数约束、冲突和方案违规可以人工标注，便于做硬评测。
- 能围绕需求判断、工作流、模型边界、评测和坏案例迭代建立完整、可验证的产品闭环。

### 4.2 目标用户

- 本节描述的是当前“工作 → 产品与研发”MVP 分支的用户，不代表 Resolve 整个平台只面向产品经理。
- 主要用户：需要组织复杂产品决策的产品经理、项目负责人或产品负责人。
- 参与用户：研发、算法、设计、业务、运营、风控、法务等提供观点或专业判断的人。

### 4.3 决策角色

| 角色 | 权限与责任 |
|---|---|
| 决策负责人 | 创建决策、选择是否继续需求、决定是否带缺失意见继续、确认最终方案、承担取舍责任 |
| 普通参与者 | 提交目标、立场、约束、偏好、证据和异议；确认 AI 对本人观点的理解 |
| 专业意见方 | 对技术、算法、风控、法务等专业边界提供证据和判断 |
| 否决权持有者 | 仅在预先指定的专业硬约束范围内拥有否决权 |

角色是现实参与者，不等于系统 Agent。MVP 不实现复杂企业权限，但数据模型必须支持上述差异。

## 5. 用户问题与核心任务

### 5.1 核心问题

> 在多方意见、证据和约束混杂且持续变化时，如何在不遗漏关键条件、不把偏好误当底线、不被未经验证的要求带偏的情况下，形成一份可执行、可解释、可追溯的产品决定？

### 5.2 用户核心任务

当我负责一次复杂产品决策时，我希望系统能：

1. 让我和参与者用自然语言表达问题，不必先学习复杂表单。
2. 将各方表达结构化，并让本人确认 AI 没有理解错。
3. 先判断需求的证据、价值、成本和风险是否足以进入后续决策。
4. 清楚展示真正的冲突、潜在冲突和缺失信息。
5. 只问少量但高价值的问题，减少无意义来回沟通。
6. 提供多个权衡方向不同、且经过约束校验的候选方案。
7. 收集可解释的接受、顾虑和反对意见，并根据新信息局部重算。
8. 由我做最终选择，并生成完整决策记录和重新打开条件。

## 6. 产品目标与非目标

### 6.1 V1 产品目标

- 跑通完整决策闭环，而不只做意见汇总或方案生成。
- 将关键判断转成结构化、可确认、可更新的决策状态。
- 在重要节点明确暂停等待人类，而不是默认全自动。
- 用独立校验降低方案违反硬约束、遗漏参与者和偷用假设的概率。
- 支持新增参与者、观点变化、新证据和约束变化后的局部重新分析。

### 6.2 V1 非目标

- 不做生活、学习场景的完整产品流程。
- 不做单人复杂决策模式。
- 不做飞书、Slack、Teams、Jira 等外部接入。
- 不做实时会议、语音、视频、群聊或消息推送。
- 不做完整公司组织架构、单点登录和精细权限系统。
- 不做 Agent 代表真实参与者自动谈判。
- 不承诺 AI 能自动得出“正确答案”或自动达成共识。
- 不做真实线上支付或商业化套餐。

## 7. MVP 支持的产品决策类型

V1 优先覆盖以下高频冲突：

| 冲突类型 | 示例 |
|---|---|
| 需求优先级 | 多个高优先级需求竞争同一研发周期 |
| 功能范围 × 上线时间 | 两周上线与四周完整开发周期冲突 |
| 用户/业务价值 × 实现成本 | 价值可能高，但证据不足且成本很大 |
| 模型效果 × 成本/延迟 | 更好效果需要更高推理成本或更长等待 |
| 上线速度 × 风险 | 业务希望尽快上线，技术、风控或法务认为风险不可接受 |
| 定制化 × 标准化 | 大客户定制机会与长期产品维护成本冲突 |

系统的数据模型也要能表达体验与成本、短期收益与长期架构、增长与用户体验、个性化与隐私、资源竞争、指标冲突等类型，但这些不作为 V1 首轮完整评测的硬要求。

## 8. 完整决策生命周期

| 阶段 | 关键问题 | 主要产物 |
|---|---|---|
| 1. 界定 | 到底要决定什么？ | 决策目标 |
| 2. 收集 | 各方在说什么？ | 原始输入 |
| 3. 结构化 | 目标、立场、诉求、约束和偏好分别是什么？ | 结构化决策状态 |
| 4. 验证 | 需求、约束和证据真的成立吗？ | 证据与假设状态 |
| 5. 需求判断 | 这个需求是否值得继续？ | 继续/补证据/暂缓/拒绝 |
| 6. 诊断 | 真正冲突在哪里？ | 冲突地图 |
| 7. 澄清 | 缺什么信息才能继续？ | 关键问题 |
| 8. 探索 | 有哪些不同权衡方向的方案？ | 候选方案集 |
| 9. 校验 | 方案是否违规、遗漏或不可执行？ | 约束审核结果 |
| 10. 审阅 | 各方是否接受，为什么？ | 接受/有顾虑地接受/反对 |
| 11. 处理异议 | 异议是否带来新约束、新证据或假设失效？ | 更新方案或升级人工取舍 |
| 12. 决定 | 谁做最后选择？ | 人工最终决定 |
| 13. 记录 | 为什么这么决定？ | 正式决策记录 |
| 14. 重新打开 | 新人、新证据、新观点出现时怎么办？ | 更新后的决策状态 |

该流程不是一次性直线。任何后续阶段都可因新事件回到必要的局部阶段，不默认从头重跑。

## 9. 功能需求与优先级

### 9.1 P0：必须实现

#### F01 创建决策

- 首页允许选择工作/生活/学习，也允许直接描述正在纠结的问题。
- 直接描述后，AI 给出场景判断、决策目标和初步冲突；用户确认或修改后才创建决策空间。
- 创建时至少记录：标题、背景、决策负责人、参与者、决策方式；截止时间可选。

验收标准：用户不填写复杂表单，也能在一次确认后进入决策空间；AI 误解时可修改。

#### F02 决策空间总览

- 展示决策标题、状态、负责人、参与者提交情况和当前阶段。
- 展示完整阶段进度，避免用户在多轮流程中迷失。
- 展示影响决策的最新变化和需要负责人处理的事项。

验收标准：用户在一个页面能回答“现在到哪一步、缺谁、下一步做什么”。

#### F03 参与者输入与本人确认

- 每位参与者可用自然语言说明目标、立场、不可接受情况、原因、证据和可妥协项。
- AI 转换为：目标、当前立场、真实诉求、声称的约束、偏好、证据、假设。
- 参与者必须确认或修改自己的结构化结果。
- 低置信度的硬约束必须标记并追问，未经确认不得升级为已验证硬约束。

验收标准：任何进入冲突分析的关键观点都能追溯到原输入和本人确认版本。

#### F04 需求判断

- 在进入方案协商前生成需求卡片：提出的方案、试图解决的问题、用户/业务证据、预期价值、成本、风险、战略关联、关键假设。
- 输出需求成熟度与理由，但不替负责人作价值决定。
- 决策负责人选择：进入后续决策、要求补充证据、暂缓、拒绝。

验收标准：系统能够指出“证明了问题存在”不等于“证明了某个指定方案必要”。

#### F05 冲突地图

- 区分已知冲突、潜在冲突和信息缺口。
- 每个冲突显示：冲突变量、涉及观点或约束、严重程度、证据状态、受影响方案。
- 无明显冲突时不得编造；应显示可直接进入方案整理或等待补充信息。

验收标准：用户能看到冲突发生在什么变量上，而不是只看到“某两个人不同意”。

#### F06 主动澄清

- 每轮最多提出 1—3 个高价值问题。
- 每个问题说明提问对象、为什么重要、答案可能影响什么。
- 关键问题未回答时，可进入“需要更多信息”，而不是强行生成结论。

验收标准：问题数量有上限，且每个问题都对应已识别的信息缺口或潜在冲突。

#### F07 候选方案与比较

- 输出 2—3 个权衡方向不同的方案，而不是同一方案换措辞。
- 每个方案统一展示：目标满足程度、满足的硬约束、牺牲的偏好、成本、风险、依赖假设、实施前提、值得考虑的原因。
- 支持横向比较。

验收标准：信息不足时明确提示假设和风险；已知无解时不得伪造可行方案。

#### F08 独立约束校验

- 对每个候选方案检查：硬约束违规、未经验证假设、遗漏参与者、内部矛盾、不可执行步骤、已被需求判断否决的内容重新混入。
- 未通过时返回方案探索重新生成；无法修复时进入人工取舍或无可行解。

验收标准：最终展示给用户的“可行方案”必须附校验状态和风险说明。

#### F09 方案审阅与异议处理

- 每位参与者可选择：接受、有顾虑地接受、反对。
- 反对必须提供理由；只有“不同意”时，系统追问原因并标记为未解释异议。
- AI 将异议分类为：新事实、新约束、原约束修改、偏好、假设失效、无新信息的立场不同。
- 参与者确认 AI 是否正确理解异议。
- 新信息只触发受影响的冲突与方案重新分析。

验收标准：异议不会被简单统计为票数，也不会覆盖历史状态。

#### F10 最终决策记录

- 仅由决策负责人确认最终方案。
- 允许负责人选择非 AI 推荐方案或主动接受高风险，但必须记录理由。
- 决策记录包含：最终决定、原因、证据、满足与牺牲、未选方案及原因、剩余风险、未解决异议、未参与人员、已接受风险、执行责任、依赖假设、重新打开条件。

验收标准：三个月后阅读者无需翻聊天记录，也能理解当时为什么这样决定。

#### F11 动态变化与重新打开

- 支持新增参与者、参与者退出或变为不活跃、观点修改、新证据、约束变化。
- 历史只追加版本，不直接覆盖。
- 系统先做影响分析，再局部重新运行必要环节。
- 已完成决策出现重要变化时，提示并由负责人确认是否重新打开。

验收标准：能展示“什么变了、影响了哪些冲突/方案、为什么需要重算”。

### 9.2 P1：应当实现

- 快速决策模板。
- 方案横向比较视图。
- 决策历史时间线和版本差异。
- 信息可见性字段：公开、仅负责人可见、仅 AI 可见；V1 先预留，不承诺完成复杂隐私调解。
- 冲突、问题、方案和异议之间的影响关联。

### 9.3 P2：后续探索

- 飞书、Slack、Teams、Jira、Notion 接入。
- 单人复杂决策模式。
- 生活和学习完整场景模块。
- 更多决策机制：全员接受、多数同意、无重大异议。
- 参与者授权的代理 Agent。
- 企业知识库、真实组织权限和审计。

## 10. 核心数据模型

```text
决策案例
├── 元信息：场景、负责人、状态、截止时间、决策方式
├── 参与者[]：角色、参与状态、当前观点、版本、提交状态
├── 目标[]
├── 真实诉求[]
├── 立场[]
├── 约束[]：声称/已验证、证据、所有者、置信度、可见性
├── 偏好[]
├── 证据[]
├── 假设[]：验证状态、影响范围
├── 未知信息[]
├── 需求[]：成熟度、需求判断状态
├── 冲突[]：类型、严重度、状态、受影响对象
├── 候选方案[]：版本、权衡、校验状态
├── 异议[]：分类、解释状态、影响范围
├── 最终决策
└── 历史事件[]
```

大模型不负责“记住所有聊天”；程序维护结构化状态、版本、事件和确定性规则。

## 12. 必须的人机协同节点

1. AI 第一次理解参与者观点后，由本人确认。
2. 低置信度或影响重大的硬约束，由相关人确认或补充证据。
3. 需求是否进入后续决策，由决策负责人确认。
4. AI 对异议的理解，由异议提出者确认。
5. 最终方案和已知风险，由决策负责人确认。

## 13. 决策状态与停止条件

### 13.1 允许的阶段性/最终结果

| 结果 | 含义 | 下一步 |
|---|---|---|
| 已形成决策 | 信息足够且负责人已确认 | 生成记录并进入已完成 |
| 需要更多信息 | 缺少影响重大的证据或回答 | 等待指定人员补充 |
| 需要人工取舍 | 目标无法同时满足，但可通过放松变量继续 | 负责人明确牺牲项 |
| 当前无可行解 | 已验证硬约束相互矛盾 | 修改至少一个硬约束后重开 |

### 13.2 Agent 必须暂停的情况

- 关键参与者输入缺失且负责人未授权继续。
- 影响重大的约束置信度低。
- 已验证硬约束相互矛盾。
- 需求价值需要负责人判断。
- 重大异议无法通过新信息或方案调整解决。
- 等待最终决定。

## 14. 异常与边界规则

| 情况 | 产品规则 |
|---|---|
| 参与者未提交 | 显示覆盖率和可能遗漏的领域；负责人选择等待或带风险继续；最终记录注明 |
| 新参与者中途加入 | 收集并确认新观点，做影响分析，只重算受影响部分 |
| 参与者修改观点 | 保留旧版本，显示变化原因和影响 |
| 参与者退出 | 标记不活跃，保留此前输入和历史 |
| 声称“绝对不能变”但无证据 | 保留为声称的约束，不自动升级为已验证约束 |
| AI 无法区分约束与偏好 | 标记不确定并追问，不能硬猜 |
| AI 理解错用户 | 本人可直接修改；未确认内容不得进入关键分析 |
| 需求无价值证据 | 进入需求挑战；AI 不自行拒绝 |
| 硬约束互相矛盾 | 明确“当前无可行解”，要求修改时间、范围、资源等至少一项 |
| 方案依赖未经验证假设 | 显著标记；高影响时禁止标记为可行方案 |
| 只有“我不同意” | 追问原因，暂记为未解释异议 |
| 否决权持有者反对 | 若落在其指定专业约束范围，阻止直接完成并升级负责人处理 |
| 负责人选择高风险方案 | 允许，记录 AI 风险提示、人工理由和已接受风险 |
| 决策后出现新证据 | 不修改旧记录；提示重新打开并创建新版本 |
| 恶意、无关或极低质量输入 | 标记无法解析并要求重新填写，不将其解释成正式观点 |
| 多轮仍不收敛 | 停止自动循环，转为人工取舍 |

## 15. 隐私与信息可见性

长期产品允许参与者将敏感底线标记为“仅 AI 可见”，系统只向其他参与者公开必要影响，例如“当前方案违反一项已确认预算约束”，而不公开原话或数值。

V1 仅预留可见性字段和入口。原型不得声称已经具备完善的企业级保密、安全或权限隔离能力。

## 16. 产品指标

### 16.1 产品可用性

- 决策流程完成率
- 各阶段放弃率
- 首次观点确认修改率
- 澄清问题回答率
- 方案审阅完成率
- 平均决策轮次和耗时
- 重新打开率及原因
- 决策负责人对“决策更清晰”的评分

### 16.2 决策质量代理指标

- 关键参与者覆盖率
- 已验证硬约束覆盖率
- 未解释异议率
- 最终记录完整率
- 信息不足时错误给结论的比例
- 高风险方案的人为覆盖及记录率

满意度和共识率不能单独代表决策质量。

## 17. AI 评测要求

后续建立 ResolveBench，首版 30—50 个产品决策案例，并加入少量生活、学习案例测试迁移潜力。每个案例人工标注硬约束、偏好、未经支持的说法、冲突、缺失信息、违规方案和关键异议。

至少比较三组：

1. 一次性聊天回答。
2. 单 Agent 完整工作流。
3. Resolve 功能型多 Agent 工作流。

核心指标包括：约束提取精确率/召回率/F1、硬约束与偏好分类、冲突精确率/召回率、信息缺口召回率、澄清问题效用、硬约束违规率、校验召回率、未经验证假设使用率、异议分类准确率、重新求解成功率、成本与延迟。

如果多 Agent 相对单 Agent 收益有限，应合并职责以降低成本和延迟，而不是为了保留架构而忽略实验结果。

## 18. MVP 页面范围

V1.2 本地 MVP 包含十一个页面/视图：

1. 首页
2. 工作领域目录
3. 产品与研发决策入口
4. 创建决策与 AI 理解确认
5. 决策空间总览
6. 参与者输入与本人确认
7. 需求判断
8. 冲突地图

产品与研发入口中的模板是可跳过的输入辅助，不是完整分类。任何产品决策都可以直接描述，由 AI 在创建阶段识别目标、参与者、冲突和标签。

## 19. V1 发布门槛

- 十一个页面可以点击走通一个“AI 自动退款”标准案例。
- 至少覆盖一次观点确认、一次需求判断、两个冲突、一个澄清问题、三个候选方案、一次异议和一次局部重算。
- 可以演示“需要更多信息”“人工取舍”“无可行解”三种非成功状态。
- 最终能生成结构完整的决策记录。
- 产品文案不得暗示 AI 拥有最终决策权或已达到企业级安全能力。

## 20. 主要风险与验证计划

| 风险 | 当前判断 | V1 验证方式 |
|---|---|---|
| 用户不愿进入新决策空间 | 高 | 用 5—8 名目标用户走查创建和协作流程 |
| 流程太长、用户中途放弃 | 高 | 记录阶段放弃率；允许负责人带风险继续 |
| AI 将偏好错判为硬约束 | 高 | 本人确认 + 标注集评测 |
| AI 为了折中忽略少数方 | 高 | 参与者覆盖率、少数约束遗漏率、独立校验 |
| 方案看似合理但不可执行 | 高 | 硬约束违规率、专业人员评审、坏案例库 |
| 多 Agent 增加成本但无质量收益 | 中高 | 与单 Agent 做同模型对照实验 |
| 通用引擎只对产品场景有效 | 中 | 加入生活、学习案例做跨场景迁移测试 |

## 22. 待验证而非待拍板的问题

- 每轮最多 3 个澄清问题是否仍然过多？
- 哪些信息必须所有参与者可见，哪些可以保密？
- 负责人决策制下，否决权如何做到足够清晰又不过度复杂？
- 用户更愿意从模板开始，还是直接描述问题？
- 冲突地图使用卡片、关系图还是两者结合，哪种更容易理解？
- 多 Agent 相比单 Agent 的真实质量收益是否足以覆盖延迟与成本？

这些问题通过界面走查和评测回答，不凭感觉继续扩功能。

## 23. V0.7 实现对照

当前已经真实实现：自然语言创建、参与者切换与确认、需求判断、冲突与澄清、方案生成、独立方案检查、补充证据后重新生成、方案选择、各方方案审阅、异议影响分析、负责人最终确认、事件历史和 SQLite 恢复。

程序会阻止以下不合法状态：仍有参与者未确认、所选方案违反硬约束或缺少关键证据、异议尚未处理、异议使当前方案失效，以及最终记录字段不完整。满足硬约束但需要负责人主动接受代价的方案会明确标为“需负责人取舍”，由人确认后才能继续。自定义流程只接受真实模型结果；模型失败时保留输入并允许重试，不自动替换为预置内容。

当前尚未实现：真实账号与多人协作、企业权限、完整的版本重开与自动局部再生成、跨场景完整流程、公开部署和真实用户验证。预置案例用于无密钥浏览，不计入模型评测结果。
