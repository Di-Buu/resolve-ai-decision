# Resolve AI 方案与评测设计

> 版本：V1.1  
> 更新日期：2026-09-10  
> 依据：《Resolve Mini PRD V1.2》  
> 状态：V0.7 已实现结构化调用、状态门槛、SQLite 记录和证据不足后的重算；已完成三模型对比、稳定性复测、Holdout 检查及 3 个纵向流程试跑

## 1. 设计目标

Resolve 的 AI 系统不是一次性“综合大家意见给出最佳方案”，而是在持续变化的决策过程中：

1. 将非结构化表达转换为可确认的结构化状态。
2. 判断哪些说法是事实、证据、假设、偏好或声称的约束。
3. 主动决定下一步最值得问什么。
4. 探索多个不同权衡方向的方案。
5. 独立检查方案是否违规、遗漏或不可执行。
6. 在异议和新信息出现后，只重新处理受影响部分。
7. 在信息不足、需要价值取舍或没有可行解时停止并交还给人。

## 2. 三层架构

| 层级 | 职责 | MVP |
|---|---|---|
| 平台层 | 工作/生活/学习入口、决策空间、用户与权限、页面状态 | 基础实现 |
| 通用决策引擎 | 结构化、验证、冲突、澄清、方案、校验、异议、重算 | 核心实现 |
| 场景知识模块 | 场景术语、典型冲突、专业规则、示例和提示 | 只做产品与研发 |

新增旅行或小组作业场景时，应复用通用决策引擎，只替换或增加场景知识模块，而不是重新开发一套“旅行 Agent”或“学习 Agent”。

## 3. 总体工作流

```text
原始输入
  ↓
结构化 Agent
  ↓ 本人确认
需求挑战与判断 Agent
  ↓ 负责人决定是否继续
冲突与澄清 Agent
  ├─ 信息不足 → 等待人类补充
  ├─ 硬约束互斥 → 无可行解 / 人工修改约束
  └─ 信息足够
       ↓
方案探索 Agent
       ↓
独立校验 Agent
  ├─ 未通过 → 返回方案探索
  └─ 通过
       ↓
参与者审阅
  ├─ 无重大异议 → 负责人最终决定
  └─ 有异议 → 异议处理 Agent → 局部重算
       ↓
决策记录生成
```

状态引擎负责路由和暂停，Agent 不可自行越过必须的人类确认点。

## 4. 功能型 Agent 分工

这些 Agent 是逻辑职责，不是现实参与者，也不要求实现时必须对应六个独立模型进程。若评测证明合并调用更好，应合并。

### 4.1 结构化 Agent

职责：

- 提取决策目标、当前立场、真实诉求、目标、偏好、声称的约束、证据和假设。
- 保留原文引用和来源参与者。
- 为每个判断输出置信度与待确认状态。
- 识别无法解析、互相矛盾或可能恶意的输入。

输入：原始描述、参与者身份、场景知识。  
输出：结构化观点草稿。  
禁止行为：未经本人确认，将“必须”“肯定”等措辞直接升级为已验证硬约束。

### 4.2 需求挑战与判断 Agent

职责：

- 区分用户/业务问题与提出的解决方案。
- 分析用户价值、业务价值、证据强度、战略关联、成本、风险、机会成本和关键假设。
- 输出需求成熟度、缺失证据和建议动作。

输入：需求、目标、证据、约束、场景知识。  
输出：需求卡片和分析建议。  
禁止行为：自行拒绝、批准或决定需求优先级。最终动作由决策负责人选择。

### 4.3 冲突与澄清 Agent

职责：

- 识别直接冲突、潜在冲突、资源竞争、时间依赖、指标冲突、约束互斥和假设不一致。
- 区分“观点不同”和“无法同时满足”。
- 识别信息缺口，并选择信息价值最高的问题。
- 每轮最多输出 1—3 个问题，说明对象、理由和可能影响。

输入：已确认决策状态。  
输出：冲突地图、信息缺口、下一轮问题或停止建议。  
禁止行为：信息不足时伪造冲突或强行生成方案。

### 4.4 方案探索 Agent

职责：

- 在已确认约束下探索 2—3 个权衡方向明显不同的候选方案。
- 标明每个方案满足、牺牲和依赖什么。
- 显式输出成本、风险、实施前提和关键假设。
- 在无法满足所有硬约束时，输出需要放松的变量，不生成“看似折中”的假方案。

输入：决策目标、约束、偏好、冲突、证据和假设。  
输出：结构化候选方案。  
禁止行为：选择最终方案；隐藏违反偏好的代价；将未经验证假设写成事实。

### 4.5 独立校验 Agent

职责只有一个：找问题。

- 检查硬约束违规。
- 检查是否把偏好误当约束，或把假设当事实。
- 检查是否遗漏参与者、异议或否决范围。
- 检查方案内部矛盾和执行不可行性。
- 检查被需求判断暂缓或拒绝的内容是否偷偷回到方案。

输入：完整决策状态和候选方案，不读取方案探索 Agent 的隐藏推理。  
输出：通过/不通过、违规类型、证据、影响和修正建议。  
禁止行为：为了让方案通过而自行修改硬约束。

### 4.6 异议处理 Agent

职责：

- 将异议分类为新事实、新约束、原约束修改、偏好、假设失效或无新信息的立场不同。
- 生成对异议的结构化理解，等待提出者确认。
- 做影响分析，决定返回验证、冲突、澄清、方案或人工取舍哪个节点。
- 连续无新信息时停止自动循环。

输入：当前方案、异议、新证据和历史版本。  
输出：异议卡、受影响对象、建议路由。  
禁止行为：默认所有反对都等价；无限生成新折中方案。

### 4.7 决策记录生成器

决策记录生成不作为独立自治 Agent。它使用固定字段模板加一次受约束的语言整理，生成决定、理由、证据、未选方案、权衡、风险、异议、责任人和重开条件。程序校验必填字段，负责人最终确认。

## 5. 确定性状态引擎

### 5.1 为什么需要

模型上下文不是可靠数据库。以下内容必须由程序管理：

- 当前阶段和允许的下一阶段
- 用户角色与操作权限
- 观点、约束、方案和异议版本
- 每次人类确认
- 对象之间的影响关系
- 已完成的决策记录
- 重新打开事件

### 5.2 事件驱动重算

系统接收以下事件：

- 参与者加入/退出
- 观点更新
- 新证据
- 约束更新
- 异议确认
- 截止时间或范围变化

每次事件先生成影响集合：

```text
事件 → 受影响约束/假设 → 受影响冲突 → 受影响方案 → 需要重跑的 Agent
```

不受影响的对象保留原版本和校验结果。

### 5.3 硬规则示例

- 未经本人确认的关键观点不得进入最终方案校验。
- 已验证硬约束互斥时不得调用方案探索生成“可行方案”。
- 高影响未验证假设存在时，方案必须标记风险；命中专业否决范围时不得完成。
- 最终决定只能由决策负责人提交。
- 已完成记录不可覆盖，只能通过新版本重新打开。

## 6. 场景知识模块：产品与研发

V1 模块包含：

- 高频冲突词表：范围、工期、资源、效果、成本、延迟、体验、风险、隐私、合规、技术债、定制化、指标。
- 典型证据类型：用户研究、行为数据、合同、技术估时、模型评测、成本测算、风控/法务规则。
- 常见误区：把老板偏好当硬约束；把竞品功能当用户需求；把期望准确率当已具备能力；忽略维护成本；用投票替代专业风险判断。
- 专业否决示例：法律禁止、安全红线、已确认风控规则。

知识模块用于提高识别与提问质量，不可将通用经验冒充当前案例事实。

## 7. 结构化输出契约

所有 Agent 必须输出可校验结构，不直接返回一大段散文。每个核心对象至少包含：

```text
id
type
statement
source_ids[]
owner_id
status

```

## 8. 人机协同与停止机制

必须中断等待人类的节点：

1. 本人确认 AI 对观点的理解。
2. 重要低置信度约束的确认或证据补充。
3. 决策负责人进行需求判断。
4. 异议提出者确认异议结构化结果。
5. 决策负责人进行最终确认。

此外，出现关键输入缺失、专业否决、硬约束互斥、纯价值分歧或连续无新信息时，系统必须停止自动循环。

## 9. 失败与降级策略

| 失败 | 降级方式 |
|---|---|
| 结构化输出格式错误 | 自动重试一次；仍失败则保留原文并允许人工填写字段 |
| 单个 Agent 超时 | 保留已有状态，提示稍后重试，不推进阶段 |
| 冲突分析置信度低 | 标记潜在冲突并生成确认问题 |
| 方案校验不通过 | 只返回失败方案重做；保留通过方案 |
| 连续两次校验失败 | 停止循环，显示失败原因和人工处理入口 |
| 异议多轮无新信息 | 转为人工取舍 |
| 状态写入失败 | 不展示“已保存”，禁止离开前继续写入 |
| 场景知识不足 | 回退通用决策引擎，并显式降低置信度 |

模型未配置或调用失败时，不生成固定替代结果。系统保留用户输入、记录失败任务与错误码，并允许重试或手动继续；预置案例只通过明确入口打开。

## 10. 评测要回答的问题

评测不是为了证明“多 Agent 一定更好”，而是回答：

1. 系统能否可靠识别硬约束、偏好、冲突和信息缺口？
2. 它能否在信息不足时停止，而不是给出虚假确定的答案？
3. 候选方案是否更少违反硬约束、偷用假设或忽略少数意见？
4. 独立校验是否真的能发现方案生成阶段的错误？
5. 多 Agent 相比单 Agent 和一次性聊天，质量提升是否值得成本和延迟？
6. 通用决策能力能否迁移到生活和学习场景？

## 11. ResolveBench 数据集设计

### 11.1 Core：产品与研发核心集

首版目标 40 个案例：

- 24 个开发集：用于提示和规则迭代。
- 8 个验证集：用于选择版本，不进入提示示例。
- 8 个测试集：在方案冻结前保持不可见。

案例均覆盖至少两个参与者、两个目标或约束，并包含一个可明确标注的冲突、信息缺口、假设或无解条件。

### 11.2 Transfer：跨场景迁移集

首版目标 40 个案例：

- 20 个工作案例：项目资源、团队协作、商务等非产品研发决策。
- 10 个生活案例：旅行、聚餐、共同消费、家庭选择。
- 10 个学习案例：小组作业、选题、分工、竞赛和学习计划。

迁移集不用于调优产品场景提示。它用于判断通用引擎是真正跨域，还是只学会了产品术语。

### 11.3 每个案例的标注

```text
决策目标
参与者与决策角色
立场
真实诉求
硬约束
软偏好
声称但未验证的约束
证据
未经支持的说法
关键假设
已知冲突
潜在冲突
必要信息缺口
高价值澄清问题
不可行方案及违规原因
可行方案边界
异议类别
正确停止状态
```

每条标注都保留文本依据和标注理由。存在合理分歧时允许多标签或“有争议”，不强造唯一答案。

### 11.4 标注质量

- 每个测试案例至少由两人独立标注。
- 对硬约束、冲突和违规方案计算标注一致性。
- 分歧由第三人讨论裁决，并保留原始分歧。
- 产品、研发、算法、风控等专业案例邀请相应背景的人抽样复核。

## 12. 对照实验

### 12.1 实验组

| 组别 | 工作方式 |
|---|---|
| A：一次性聊天 | 所有材料一次输入，直接要求给出最佳方案 |
| B：单 Agent 工作流 | 同一 Agent 按结构化、冲突、澄清、方案、校验顺序处理 |
| C：Resolve | 功能型 Agent 分工 + 确定性状态引擎 + 人机确认 |

### 12.2 公平比较原则

- 三组尽量使用同一基础模型和相同输入信息。
- 固定或记录温度、提示版本、模型版本和运行日期。
- 不给 Resolve 组额外隐藏事实。
- 每个案例多次运行，报告平均值和波动，不挑最好结果。
- 同时报告质量、延迟和成本。

### 12.3 消融实验

在 Resolve 组内依次移除：

- 本人确认
- 需求判断
- 主动澄清
- 独立校验
- 结构化状态与局部重算

观察每个模块对质量、延迟和成本的影响。若某模块收益有限，考虑合并或删除。

## 13. 核心指标

### 13.1 理解与结构化

| 能力 | 指标 | 说明 |
|---|---|---|
| 约束提取 | 精确率、召回率、F1 | 是否找全且不过度提取 |
| 硬约束/偏好分类 | 宏平均 F1 | 避免用类别不平衡掩盖问题 |
| 未经支持说法识别 | 精确率、召回率 | 能否指出缺少证据的要求 |
| 证据/假设区分 | 准确率、宏平均 F1 | 防止将推测写成事实 |
| 参与者覆盖 | 关键诉求覆盖率 | 是否遗漏少数或不活跃参与者 |

### 13.2 冲突与澄清

| 能力 | 指标 | 说明 |
|---|---|---|
| 冲突识别 | 精确率、召回率、F1 | 对比人工标注冲突 |
| 信息缺口 | 召回率 | 高影响缺口优先，漏掉比多问更危险 |
| 澄清问题 | 必要性、信息增益、对象正确性、重复率 | 人工按统一量表评分 |
| 停止判断 | 状态准确率 | 是否正确选择继续、补信息、人工取舍或无解 |

### 13.3 方案与校验

| 能力 | 指标 | 说明 |
|---|---|---|
| 硬约束违规 | 方案违规率 | 至少违反一个已验证硬约束的方案占比 |
| 未经验证假设使用 | 假设泄漏率 | 将未验证假设作为事实的方案占比 |
| 方案可行性 | 专家可执行评分 | 是否可在给定条件下执行 |
| 方案多样性 | 权衡差异评分 | 防止三个方案只是换措辞 |
| 独立校验 | 违规检出召回率、误报率 | 能否发现预埋或生成的错误 |

### 13.4 异议与重算

| 能力 | 指标 | 说明 |
|---|---|---|
| 异议分类 | 宏平均 F1 | 新事实、新约束、偏好、假设失效等 |
| 影响分析 | 受影响对象准确率 | 是否重算正确部分 |
| 重新求解 | 成功率 | 新信息后能否生成仍满足约束的方案 |
| 最小重算 | 无关对象保留率 | 不应无理由改写未受影响内容 |
| 循环控制 | 无效循环率 | 无新信息时是否停止 |

### 13.5 公平性与 AI 引导风险

- 少数意见遗漏率。
- 否决权范围误用率。
- 不同表达风格参与者的诉求覆盖差异。
- AI 首先展示某方案后，人工选择是否出现异常偏移。
- AI 是否在未说明的情况下改变价值权重。

用户“觉得讨论更顺畅”不代表决策质量更高。这组指标必须与满意度同时报告。

### 13.6 系统成本

- 单案例总模型调用次数。
- 输入/输出 token 成本。
- 首次结构化响应时间。
- 完整流程总时长。
- 人工介入次数。
- 失败重试率。

## 14. V1 目标门槛

以下是发布前目标，不是当前已经达到的结果：

| 指标 | 目标 |
|---|---:|
| 已验证硬约束召回率 | ≥ 0.90 |
| 硬约束/偏好分类宏平均 F1 | ≥ 0.85 |
| 冲突召回率 | ≥ 0.85 |
| 高影响信息缺口召回率 | ≥ 0.85 |
| 通过校验后的方案硬约束违规率 | ≤ 0.05 |
| 独立校验违规检出召回率 | ≥ 0.90 |
| 未经验证假设泄漏率 | ≤ 0.10 |
| 停止状态准确率 | ≥ 0.85 |

若未达到门槛，先分析错误分布，不因接近目标就改标注或删除困难案例。

## 15. 人工评分量表

### 15.1 澄清问题效用（1—5 分）

- 1：无关、重复或无法回答。
- 2：有一定相关性，但不影响决策。
- 3：能补充背景，影响有限。
- 4：明显减少不确定性或排除一个方案方向。
- 5：直接决定约束有效性、方案可行性或停止状态。

### 15.2 方案可行性（1—5 分）

- 1：违反关键条件或不可执行。
- 2：存在重大遗漏，需要重写。
- 3：大体可行，但仍需重要补充。
- 4：条件明确、风险可控，可进入评审。
- 5：在给定信息下完整、可执行且权衡透明。

### 15.3 解释质量（1—5 分）

检查结论是否能追溯到证据、是否说明牺牲与风险、是否明确不确定性，而不是只看语言是否流畅。

## 16. 标准评测案例示例

### 输入摘要

业务要求双十一前上线全自动退款；研发确认完整能力至少四周，当前只有两周；风控规定 500 元以上退款必须人工审核；产品希望尽量减少人工操作。

### 标注摘要

- 硬约束：两周内上线；500 元以上人工审核。
- 偏好：自动化覆盖越高越好；减少人工操作。
- 冲突：完整范围与时间；全自动与风控规则。
- 信息缺口：500 元以下退款占比；风险分类模块工期。
- 正确状态：需要更多信息。
- 违规方案：两周内所有退款全自动处理。

### 动态事件

研发新增证据：风险分类模块需要三周。正确行为是标记依赖“两周可完成分类”的方案失效，并局部重算；不应重写风控规则或已确认的业务目标。

## 17. 坏案例分类

每次失败至少归入一种：

- 抽取遗漏
- 硬约束/偏好误判
- 证据与假设混淆
- 虚假冲突
- 冲突遗漏
- 低价值或重复追问
- 信息不足却强行结论
- 方案硬约束违规
- 忽略少数参与者
- 独立校验漏检/误报
- 异议分类错误
- 重算范围过大或过小
- 无限循环
- 人机权限越界
- 状态或版本错误

坏案例记录：案例编号、模型和提示版本、实际输出、期望输出、影响、根因、修复、回归结果。

## 18. 版本与实验记录

每次实验固定记录：

- 数据集版本与划分
- 模型名称和版本
- Agent/提示版本
- 规则版本
- 运行参数
- 指标结果
- 成本和延迟
- 失败案例列表
- 结论和下一步调整

不同版本只允许在同一不可见测试集上进行有限次数正式评估，避免不断针对测试集调参。

## 19. 第一轮实现顺序

1. 定义决策状态、对象编号和版本规则。
2. 实现结构化 Agent 与本人确认。
3. 实现需求判断和负责人中断。
4. 实现冲突、澄清和停止状态。
5. 实现方案探索与独立校验闭环。
6. 实现异议确认、影响分析和局部重算。
7. 实现固定字段的决策记录。
8. 构建 10 个冒烟案例，再扩展 ResolveBench。
9. 运行一次性聊天、单 Agent、Resolve 三组对照。
10. 根据质量、成本和延迟决定是否合并 Agent。
